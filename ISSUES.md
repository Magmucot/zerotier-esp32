## [x] P0-1 — Печать производных симметричных ключей сессии в лог [ДЕФЕКТ]

- **Приоритет:** P0
- **Где:** `ZeroTierOne/node/Peer.cpp:24–29` (макросы по умолчанию = 1), `:89–95` (K0, `[ZT_STEP46_K0_DERIVED] hex=`), `:103–109` (K1, `[ZT_STEP46_K1_DERIVED]`), `:111–112` (key16 и fingerprint); `IncomingPacket.cpp:35–36`, `Topology.cpp:18–19`.
- **Причина:** отладочный код (STEP45/46) остался в ядре и включён по умолчанию; печать выполняется без условия сборки, только по адресу контроллера.
- **Последствия:** любой, кто имеет доступ к UART/логам (физически или через журналирование), получает ключи сессии с этим пиром и может расшифровывать/подделывать трафик этой сессии. Это не раскрывает приватный ключ identity, но раскрывает сессионный материал.
- **Доказательства:** строка `ZT_STEP46_K0_DERIVED` найдена в `zt_esp32.bin` (1 совпадение); макрос по умолчанию 1 (`Peer.cpp:24–29`); `Peer.cpp` в HEAD содержит печать `hex=` для K0.
- **Воспроизведение:** собрать HEAD → `strings zt_esp32.bin | grep ZT_STEP46_K0` (найдено). На устройстве: инициировать создание Peer для адреса контроллера и прочитать лог — **не выполнено** (нет устройства).
- **Что исправить:** удалить печать ключей из ядра полностью (не только гейтировать); отладочные макросы — по умолчанию 0 и запрещены в release-конфигурации. Ротировать все ключи, которые могли попасть в логи.
- **Регрессионные тесты:** (a) CI-проверка: `strings` по `.bin` не содержит `ZT_STEP`, `_DERIVED`, `hex=`; (b) grep в CI по `printf` с ключевым материалом в `node/`; (c) хост-тест: `Peer` не пишет в stdout (перехват stdout).
- **Уверенность:** высокая (наличие кода и строки в бинарнике). Средняя — для практической эксплуатации (нужен доступ к логам).

## [x] P0-2 — Тестовый приватный ключ, встроенный в репозиторий, используется как fallback [ДЕФЕКТ]

- **Приоритет:** P0
- **Где:** `components/zerotier_node/port/zt_storage_esp.cpp:12–15` (ZT_TEST_SECRET/ZT_TEST_PUBLIC, комментарий «public and should only be used for testing»), `:66–84` (fallback для `ZT_STATE_OBJECT_IDENTITY_SECRET`/`PUBLIC`); `main/main.cpp` использует этот порт через `ZT_Node_new`.
- **Причина:** fallback «для QEMU» попал в общий код порта и не отключён в сборке устройства.
- **Последствия:** любое устройство без provisioned identity (или после стирания NVS, см. P1-3) получает **известный всем приватный ключ**: другой участник может выдать себя за узел (подделать identity и адрес ZeroTier, принимать трафик, предназначенный узлу). Противоречит заявленной политике «on-device default identity generation not a goal» (README/архитектура).
- **Доказательства:** код читается однозначно. Проверено длинами строк: `ZT_TEST_SECRET` = 270 символов (поля: адрес 10 / тип 1 / публичный ключ 128 / **приватный ключ 128**), `ZT_TEST_PUBLIC` = 141 символ (только публичная часть). То есть в репозитории лежит полный приватный ключ identity, а не просто «тестовый идентификатор».
- **Воспроизведение:** запустить порт с пустым NVS → `stateGet(IDENTITY_SECRET)` вернёт тестовый ключ (хост-тест возможен: вызвать колбэк с пустым хранилищем). Не выполнено в харнесе — только по коду.
- **Что исправить:** fail closed: при отсутствии identity возвращать `-1` и не стартовать узел; тестовую identity вынести в отдельную сборочную конфигурацию (не в release-порт); удалить `ZT_TEST_SECRET` из исходников.
- **Регрессионные тесты:** (a) хост-тест: пустой NVS → `stateGet` возвращает ошибку, `ZT_Node_new` не создаёт узел; (b) CI: release-бинарник не содержит строку тестового секрета (`strings` / grep по `df429581f6`); (c) проверка, что `ZT_ESP32` provisioning требует явного ключа.
- **Уверенность:** высокая (код). Эксплуатация требует знания, что устройство без identity — что на практике часто (первый запуск).

## [x] P0-3 — Удалённый крэш по неаутентифицированному HELLO: `abort()` в `Identity::deserialize` [ДЕФЕКТ]

- **Приоритет:** P0
- **Где:** `ZeroTierOne/node/Identity.hpp:246` (неверный тип идентичности → `abort()`), `:255` (неверный криптотокен → `abort()`), также `:49`, `:143` (ZT_EXCEPTION→abort). Вызов: `IncomingPacket.cpp:73` (`try`), `:91` (HELLO без MAC-шифра → `_doHELLO(false)`), `:492` (`id.deserialize`), `:277` (`catch (...)`). Upstream: `Identity.hpp` бросает `ZT_EXCEPTION_INVALID_SERIALIZED_DATA_INVALID_TYPE` (строка 246 в zt-ref), который ловится `catch (...)`.
- **Причина:** в ESP32-патче исключения заменены на `abort()` (вероятно, для «жёсткой» отладки), но путь принимает ввод из сети до аутентификации.
- **Последствия:** любой отправитель, способный послать UDP-пакет на порт 9993 (ZeroTier-порт, открыт на `INADDR_ANY`, `zt_socket_esp.cpp:20–45`), может вызвать перезагрузку устройства. Регулярная отправка — постоянный отказ в обслуживании. Для устройства на LAN/интернете — серьёзно.
- **Доказательства:** upstream-Identity → `RESULT: exception caught`, exit 0; патч-Identity → SIGABRT, exit 134. Путь достижим: `tryDecode` → HELLO (`cipher == C25519_POLY1305_NONE`) → `_doHELLO(false)` до проверки MAC.
- **Воспроизведение:** `bash harness/run_all.sh` (раздел 3). На устройстве: отправить HELLO с ненулевым байтом типа идентичности — **не выполнено** (нет устройства, нет сетевого стенда).
- **Что исправить:** вернуть `throw` (как в upstream) либо явно отвергать пакет в `_doHELLO`; `abort()` в библиотечном коде недопустим. Для диагностики — логировать и возвращать `false`.
- **Регрессионные тесты:** (a) хост: тест deserialize с неверным типом должен давать контролируемый результат (исключение/отказ), процесс не завершается; (b) libFuzzer/AFL на `IncomingPacket::tryDecode` с HELLO-заголовками (санитайзеры: ASan/UBSan); (c) CI-grep: `abort()` в `node/` и `osdep/` = 0.
- **Уверенность:** высокая (дифференциальный эксперимент и чтение пути). Полный «удалённый» сценарий на устройстве — средняя (не проверено на железе).

## [ ] P0-4 — Несовместимость identity: `ZT_IDENTITY_GEN_MEMORY_OVERRIDE=65536` [ДЕФЕКТ]

- **Приоритет:** P0
- **Где:** `components/zerotier_node/CMakeLists.txt:76` (`-DZT_IDENTITY_GEN_MEMORY_OVERRIDE=65536`), `ZeroTierOne/node/Identity.cpp:26–29`, `ZeroTierOne/node/Identity.cpp:108–122` (`locallyValidate` пересчитывает PoW тем же размером), `ZeroTierOne/node/IncomingPacket.cpp:573–577` (HELLO → `locallyValidate()` → «invalid identity»).
- **Причина:** уменьшение памяти PoW ради RAM ESP32; упущено, что `locallyValidate` и генерация должны использовать один параметр upstream.
- **Последствия:** (a) HELLO любого upstream-узла (включая контроллер/корневые узлы) для неизвестного пира отбрасывается → прошивка не может установить прямой путь и получить сетевую конфигурацию; (b) идентичности, сгенерированные прошивкой, не принимаются upstream; (c) заявленные QEMU-результаты (ONLINE, join, NetworkConfig) несовместимы с этим фактом и требуют объяснения (возможно, тестовый стенд использовал только собственные идентичности).
- **Доказательства:** генерация 3/3 самовалидна в обеих сборках; перекрёстная проверка: ESP32-сборка → upstream-идентичности 0/3; upstream → ESP32-идентичности 0/3; контроль upstream → своих 3/3. Встроенная тестовая identity (`zt_storage_esp.cpp`): upstream 1/1, ESP32-сборка 0/1.
- **Воспроизведение:** `bash harness/run_all.sh`, раздел «2».
- **Что исправить:** убрать override для release; оставить upstream-параметр 2 МиБ (память — PSRAM, см. раздел 7) либо генерировать и провижионировать identity вне устройства; обновить `locallyValidate` только вместе с upstream. Тестовые identity пересоздать под выбранный параметр.
- **Регрессионные тесты:** (a) хост-тест перекрёстной проверки (должен давать 3/3 при едином параметре); (b) тест-вектор HELLO от upstream (из `ZeroTierOne/selftest` или сгенерированный upstream-узлом) → прошивка/хост-харнесс принимает; (c) CI: `ZT_IDENTITY_GEN_MEMORY` не переопределён.
- **Уверенность:** высокая для совместимости identity (эксперимент). Высокая для того, что код отвергнет HELLO (чтение строк 573–577). Влияние на реальную сеть — не проверено runtime.

- **Регрессионные тесты:** (a) CI: `nm` на ELF обязан содержать `ZT_Node_join` и `zt_*`-символы выбранного dataplane; (b) интеграционный тест ARP/ICMP/UDP в QEMU (когда будет окружение); (c) тест «ZT_Node_join вызывается при старте с валидной сетью» на хосте с мок-портом.
- **Уверенность:** высокая (ELF и код). Влияние на пользователя — высокое.

## [x] P1-1 — Удаление маршрута с шлюзом не удаляет запись в таблице ESP32NetLink [ДЕФЕКТ]

- **Приоритет:** P1
- **Где:** `ZeroTierOne/osdep/ManagedRoute.cpp:599, 603` (add с `_device`), `:659` (Linux), `:664` (ESP32: `delRoute(..., (_via) ? nullptr : _device)`); `ZeroTierOne/osdep/ESP32NetLink.cpp:57–67` (нормализация device), `:110–117` (поиск по target/mask/via/src/…), `:169+` (delRoute).

- **Доказательства:** C1 (direct) PASS; C2 (via + удаление без device) — **1 запись осталась (FAIL)**; C3 (контроль: удаление с device) — 0 записей.
- **Воспроизведение:** `bash harness/run_all.sh` (раздел 1).
- **Что исправить:** удалять по (target, via, src) без зависимости от device, либо передавать одинаковый device в add и del.
- **Регрессионные тесты:** хост-тест C2 (ожидается 0 записей); тест на переполнение таблицы после многократного add/del.
- **Уверенность:** высокая (эксперимент на реальном модуле ESP32NetLink, вызовы повторяют `ManagedRoute.cpp`). Средняя для влияния на трафик (P1-2).
